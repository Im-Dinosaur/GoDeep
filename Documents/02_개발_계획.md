# GoDeep 개발 계획

작성일: 2026-09-28 · 누적 기간 기준 · 일정은 첫 시제품 평가 후 갱신

## 1. 일정과 완료 조건

| 단계 | 누적 목표 | 결과물 | 완료 판단 |
|---|---|---|---|
| M0. 환경 정리 | 시작 | 폴더, Home/StandBy/Play, Fusion·Voice SDK | 씬 빌드 목록과 컴파일 정상 |
| M1. 조작·표현 시제품 | 2~4주 | 수영, 워치, 산소팩, 짧은 동굴, 손·장비 표현 | 실제 조작 평가와 입력·충돌·산소 검증 통과 |
| M2. 4인 협동 구간 | 6~10주 | 방 생성·입장, 이동·산소·아이템·구조·부활 동기화 | 독립 클라이언트 4명이 짧은 구간 완주 |
| M3. 전체 플레이 | 12~16주 | 3개 챕터, 기믹, 에어포켓 음성, 전멸·완주 흐름 | 처음부터 끝까지 이어지는 플레이와 음성 구역 규칙 통과 |
| M4. 출시 후보 | 16~24주 | 모델·애니메이션·조명·소리, 난이도, 최적화, 출시 준비 | 회귀검사와 목표 PC 성능·사용성 검증 |

출시 목표는 약 5개월, 수정 여유를 포함한 계획은 6개월이다. 주 단위 표는 자동 작업 예약이나 보장된 납기가 아니다. 실제 조작감·모션 자산 확보·독립 클라이언트 테스트 속도에 따라 조정한다.

## 2. 이번 구현 범위: M1 첫 증분

- Home → StandBy → Play의 로컬 연습 진입 흐름.
- PC 키보드·마우스 기반 1인칭 수영, 가속·감속, 벽 충돌, 상승·하강.
- 산소 소모, 에어포켓 소모 중단, 공급 장치에서 보충.
- 빈손 우클릭 워치, 깊이·산소 확인, 4개 신호의 로컬 미리보기.
- 산소팩 자신/연습 다이버 사용, 무효 사용 시 보존, 보급품 획득.
- 손목 들기와 산소팩 사용을 구분하는 임시 절차적 팔 동작.
- 짧은 테스트 동굴, 목표 에어포켓 도착, 산소 소진·재시작.
- 실제 Unity 컴파일·상태 검증과 플레이 화면 확인.

이 증분은 온라인 로비, 실제 팀 메시지, 음성 통화, 완성형 캐릭터 애니메이션, 3개 챕터 완성을 의미하지 않는다. M1 전체 완료는 사용자의 조작·표현 평가까지 필요하다.

## 3. 구현 구조

| 진입점 / 스크립트 | 책임 |
|---|---|
| `GameFlow` | 씬 이동을 한곳에서 처리 |
| `PrototypeSession` | 연습 구간의 진행·목표·종료와 플레이어 갱신 |
| `Player` | 입력과 이동·산소·아이템·워치·표현 호출 조율, 외부 상호작용 API |
| `PlayerInputComponent` | Input System에서 입력 프레임 생성 |
| `PlayerMovementComponent` | 시점 회전, 수영 가감속과 CharacterController 충돌 이동 |
| `PlayerOxygenComponent` | 산소와 행동불가·탈락 상태, 산소 회복 |
| `PlayerItemComponent` | 손 상태, 산소팩 수량과 효과 적용 |
| `PlayerWatchComponent` | 워치 표시와 신호 기록 |
| `PlayerPresentationComponent` | 임시 팔 동작과 피드백 소리 |
| `AirPocketComponent` | 안전 공간의 범위와 식별자 |
| `DiveInteractableComponent` | 보급품과 산소 공급 장치의 상호작용 |
| `PrototypeUIComponent` | 안내·상태·진행·일시정지 화면 |

UI·장치·세션은 `Player`를 통해 기능을 사용한다. 각 Component는 필요한 값이나 대상만 전달받으며 형제 Component를 찾아 조작하지 않는다. 조절값과 씬 연결은 Inspector에서 확인 가능하게 둔다.

## 4. 다음 작업 순서

### M1 남은 작업

1. 사용자의 수영 속도·감속·시야각·워치 위치 평가 반영.
2. 1인칭 손과 전신 모델·모션 자산의 후보 및 예산 검토.
3. 수영·워치·산소 사용의 동작 전환과 사운드 개선.
4. 실제 리그가 연결된 상태에서도 이동·상호작용 검사 반복.

### M2 진입

2026-09-28 기준 Shared 모드 선택, 방 생성·코드 입장·퇴장과 플레이어 이동 동기화를 구현했다. 같은 PC의 독립 프로세스 4개로 실제 Photon 통신을 확인했다. 아래 2번의 준비 완료 투표와 4~5번의 생존 협동은 후속 작업이다. 세부 결과는 [Fusion 온라인 개발 기록](05_Fusion_온라인_개발.md)에 남긴다.

1. Fusion 모드와 상태 권한, 방장 종료·재접속 정책 결정.
2. StandBy의 실제 생성·입장·준비·퇴장 흐름 구현.
3. 네트워크 플레이어 프리팹과 입력·이동 동기화. 로컬 카메라/원격 전신 분리.
4. 산소·소모품·장치 사용을 권한 있는 시뮬레이션에서 검증.
5. 워치 신호 전송, 동료 산소 사용, 행동불가 구조, 탈락·관전·부활.
6. 2인부터 시작해 독립 실행 4인으로 확장. 지연·동시 사용·연결 종료 확인.

### M3 / M4

시야·물살·입체 길찾기 기믹을 각각 짧게 검증한 뒤 챕터를 늘린다. Photon Voice는 같은 에어포켓 ID의 유효한 플레이어 사이에서만 송수신하도록 연결하고, 입수·퇴장·재접속 때의 차단을 검사한다. 이후 콘텐츠 길이와 반복 플레이, 성능과 출시 준비를 진행한다.

## 5. 검증 기준

- 대각선 입력으로 의도보다 빨라지지 않으며 벽을 통과하지 않는다.
- 프레임 시간에 따라 산소 소모·이동량이 크게 달라지지 않는다.
- 에어포켓 진입만으로 산소통이 자동 충전되지 않는다.
- 잘못된 대상, 벽 너머 대상, 산소가 가득 찬 대상에게 사용해도 산소팩을 잃지 않는다.
- 산소팩 효과와 수량 감소가 한 번의 입력에 한 번만 일어난다.
- 빈손과 아이템 상태의 우클릭 행동이 겹치지 않는다.
- 워치를 보면서 수영할 수 있고, 입력을 놓으면 다시 내린다.
- 산소 0 → 행동불가 → 구조 또는 탈락 전이가 일관된다.
- 재시작 후 산소·보급품·시간·커서 상태가 초기화된다.
- 온라인 단계에서만 실제 접속·음성 테스트 완료를 표시한다.

## 6. 작업 위치

프로젝트의 `Documents`는 기획·계획·검증 기록을 둔다. Unity 자산은 기존 `Assets/1. Scenes`~`Assets/6. Data`를 따른다. 기존 `Assets/Document`는 보존한다. 편집기 생성 도구는 `Tools`에 두고 실제 씬·프리팹·설정 자산을 저장한다. 임시 백업·검증 산출물은 Git에서 제외된 `.utmp`에 보관한다.

기술 참고: [Unity CharacterController.Move](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/CharacterController.Move.html), [Input System 마우스 입력](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/Mouse.html). 설치된 Input System 1.20.0의 실제 API와 Unity 컴파일 결과도 함께 확인한다.
